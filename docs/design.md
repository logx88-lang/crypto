# 사내 지식 공유 RAG 플랫폼 — 상세 설계서

> 버전: v0.1 (설계 검토용 초안) · 대상 배포 환경: 오프라인(폐쇄망) Windows 11 PC
> 이 문서는 구현 착수 전 검토용이다. 미확정 사항은 `docs/open_questions.md` 참조.

---

## 0. 전제와 최우선 원칙

1. **오프라인 배포가 최상위 제약이다.** 설치 시 인터넷이 필요한 방식은 전부 실패로 간주한다.
   모든 라이브러리는 "Windows + Python 3.10~3.12 + 순수 `pip` wheel 오프라인 설치 가능"을
   1순위로 검증한다(§10 검증표).
2. **12GB RAM / 8GB VRAM에서 확실히 도는 구성이 이론상 우수한 구성보다 우선한다.**
   모든 모델 선택은 메모리 예산(§2)을 통과해야 한다.
3. **실제 사내 자료는 개발 PC에 존재하지 않는다.** 더미 샘플로만 개발/테스트하며,
   샘플은 **검토 게이트**(§12) 통과 후에만 파이프라인 확정에 사용한다.
4. **HEX 로그는 지식 문서가 아니다.** 인덱싱 대상이 아니라 질의 시 업로드되는 분석 입력물이다(§7).

### 확정된 핵심 스택 (사용자 결정)

| 구성요소 | 선택 | 근거 |
|---|---|---|
| 웹 UI | **Streamlit** | 단일 호스트 다중 사용자, 순수 wheel, 업로드+채팅+확인단계 UI 용이 |
| 임베딩 | **bge-m3 (FP16 GGUF)** | 오프라인 PC 기설치. 한/영 다국어 검색 강함 |
| 벡터 DB | **ChromaDB** | 순수 파이썬, 메타데이터 필터 편의. BM25 미내장 → 별도 결합(§5) |
| LLM 런타임 | **Ollama** | 오프라인 PC 기설치. 모델 스와핑/keep_alive로 VRAM 관리 |
| 한국어 형태소 | **kiwipiepy** | Windows wheel 제공, BM25 토큰화용 |

## 1. 전체 아키텍처

```
[인제스천 파이프라인]
  문서(xlsx/docx/pptx/txt/이미지)
    └─ 포맷별 파서 ──▶ 정규화 텍스트 + 구조 메타(표/시트/슬라이드/페이지)
        └─ (이미지) OCR ──▶ 텍스트
    └─ 청킹(표 보존, 메타 부착)
        └─ 임베딩(bge-m3) ──▶ ChromaDB(dense)  +  kiwipiepy 토큰화 ──▶ BM25 인덱스
        └─ 파일 해시/mtime ──▶ 증분 인덱싱 매니페스트

[질의 파이프라인 — 일반 문서 QA]
  사용자 질문
    └─ 하이브리드 검색: dense(ChromaDB) + BM25 → RRF 융합 → top-k
        └─ (선택) 리랭커
        └─ 컨텍스트 조립(출처 메타 포함)
        └─ LLM(Ollama) ──▶ 한국어 답변 + 출처 표기

[질의 파이프라인 — HEX 로그 분석 모드]  (§7)
  HEX 업로드 + 질문
    └─ 프로토콜 명세 후보 검색 ──▶ [UI 확인 단계] ──▶ 확정 명세 컨텍스트
        └─ HEX 파싱/구간 추출 ──▶ LLM ──▶ 분석 답변

[UI] Streamlit 단일 호스트 웹앱: 문서 QA 탭 / HEX 분석 탭 / 관리(인덱싱) 탭
```

컴포넌트 경계(모듈 구조 예정):
- `ingest/` 포맷별 파서 + 청킹
- `index/` 임베딩·ChromaDB·BM25·증분 매니페스트
- `retrieve/` 하이브리드 검색·RRF·(리랭커)
- `generate/` 프롬프트 템플릿·LLM 호출·출처 포매팅
- `hex/` HEX 파싱·프로토콜 매칭·분석
- `app/` Streamlit UI
- `packaging/` wheelhouse·설치 스크립트·smoke test·모델 이전 가이드

## 2. 메모리 예산 (VRAM 8GB / RAM 12GB)

RTX 3060 Ti는 VRAM 8GB. 질의 시 **동시에 상주해야 하는** 모델을 기준으로 예산을 잡는다.

| 모델 | 구성 | VRAM(대략) | 상주 시점 |
|---|---|---|---|
| LLM | 7~8B급 Q4_K_M | ~4.5–5.5GB | 질의(답변 생성) |
| 임베딩 bge-m3 | FP16 GGUF | ~1.3–2.2GB | 인제스천 + 질의(질문 임베딩) |
| 리랭커 bge-reranker-v2-m3 | (선택) | ~1.1–2.0GB | 질의(선택, Phase 3) |
| OCR | PaddleOCR/Tesseract | ~1–2GB 또는 CPU | **인제스천 시점만** |

**계산과 결론**
- LLM(5.0) + bge-m3(2.0) ≈ **7.0GB** → 8GB 안에서 동시 상주 **가능**, 여유 ~1GB.
- 여기에 리랭커(1.5)까지 동시는 **불가**(8.5GB 초과).
- **KV 캐시**: 7B 모델 기준 컨텍스트 1K 토큰당 대략 0.1–0.15GB. 기본 `num_ctx=4096`이면 ~0.5GB,
  8192면 ~1GB. 위 7.0GB에 KV까지 더하면 8192 컨텍스트는 빠듯 → **기본 4096**, HEX 분석 등
  긴 컨텍스트가 필요할 때만 선택적으로 상향.

**전략 (확실히 도는 구성)**
1. **Ollama 모델 스와핑 + `keep_alive` 튜닝**: 임베딩과 LLM을 시간 분할. 질의 시 질문 임베딩 →
   검색 → 답변 생성 순서라, 임베딩과 LLM의 피크가 겹치지 않게 조절 가능.
2. **임베딩을 CPU로 실행하는 옵션**: bge-m3 단건 질문 임베딩은 CPU에서도 지연이 수용 가능.
   이러면 질의 시 VRAM은 사실상 LLM 전용 → KV 캐시 여유 확보. (인제스천 대량 임베딩은 GPU 권장)
3. **리랭커는 MVP 미포함**. 도입 시 임베딩→언로드→리랭커 스와핑 또는 CPU 실행으로 처리.
4. **OCR은 인제스천 시점에만** 동작하므로 질의 시 LLM과 경합하지 않음. 인제스천은 배치로 수행.

> 실제 LLM 모델 태그와 양자화는 오프라인 PC에서 확정해야 한다(`docs/open_questions.md` Q1).
> "qwen 3.5 9b"는 공개 태그로 실재가 불명확 → 8GB VRAM 안전권인 **7~8B Q4_K_M** 계열 확정 권장.

## 3. 포맷별 파싱 전략

공통 원칙: **양식 표준이 없으므로 특정 템플릿에 의존하지 않는다.** 구조를 범용적으로 추출하고,
텍스트·표 중심으로 정규화한다. 각 청크에는 출처 메타(파일명·위치)를 부착한다.

### xlsx — `openpyxl` (순수 wheel ✓)
- 시트별로 분리 처리. 시트명을 메타로 부착.
- 표를 **마크다운 표/키-값 텍스트로 직렬화**하여 LLM이 읽기 쉽게 변환.
- **병합셀**: 병합 범위를 감지해 대표값을 각 셀에 fill-forward.
- **다중 헤더**: 상단 N행이 헤더로 보이면 계층 헤더를 `상위 > 하위` 형태로 병합해 열 이름 생성.
- 수식 셀은 계산값(있으면) 우선, 없으면 원식 텍스트.

### docx — `python-docx` (순수 wheel ✓)
- 문단/표/이미지를 추출하되 **본문 XML을 순회해 인라인 순서를 보존**(python-docx 기본 API는
  문단과 표를 분리 반환하므로, `document.element.body` 순회로 등장 순서 유지).
- 표는 xlsx와 동일하게 마크다운 직렬화.
- **비표준 스타일 대응**: 스타일 이름에 의존하지 않고 텍스트/표 내용 자체를 추출.
- 임베디드 이미지는 추출 후 OCR 파이프라인(§8)으로.

### pptx — `python-pptx` (순수 wheel ✓)
- **슬라이드 단위**로 텍스트 프레임·표·이미지 추출, **슬라이드 번호**를 메타로 부착.
- 표는 마크다운 직렬화. 이미지 shape는 OCR로.
- 발표자 노트가 있으면 별도 필드로 포함(선택).

### txt — `charset-normalizer` (순수 wheel ✓)
- 인코딩 **자동 판별**: EUC-KR/CP949/UTF-8(+BOM) 등. 판별 실패 시 CP949→UTF-8 순 폴백.
- 개행/공백 정규화 후 청킹.

### 이미지 — OCR (§8, Phase 3)
- 문서 내부 이미지(스크린샷/다이어그램)에서 한/영 텍스트 추출. **인제스천 시점** 실행.

### hex — 인덱싱 제외
- 지식 인덱스에 넣지 않는다. 질의 시 사용자가 업로드하는 분석 입력물로만 사용(§7).

## 4. 청킹 전략

- **크기/오버랩**: 한/영 혼용을 고려해 **~400–800 토큰, 10–15% 오버랩**. (토큰 길이는 bge-m3
  토크나이저 기준으로 근사. 한국어는 형태소가 많아 문자 대비 토큰 밀도가 높은 점 반영.)
- **표 보존**: 표는 **청크 경계에서 자르지 않는다.** 표 하나가 크면 표를 독립 청크로 분리하고,
  헤더를 각 분할 조각에 반복 부착해 문맥 유지.
- **경계**: 문단/슬라이드/시트 등 자연 경계를 우선 존중(문장 중간 절단 회피).
- **메타데이터(청크마다 부착)**: `source_file`, `doc_title`, `sheet_name`/`slide_no`/`page_no`,
  `section`, `doc_type`(예: `protocol_spec` | `general`), `chunk_id`, `content_hash`.
  → `doc_type`은 HEX 워크플로우에서 프로토콜 명세만 필터링하는 데 사용(§7).

## 5. 임베딩 및 검색

### 임베딩
- **bge-m3 (FP16 GGUF, 오프라인 PC 기설치)** 를 Ollama로 서빙. 1024차원.
- nomic-embed-text 대비 한국어 recall이 강해 한/영 혼용 코퍼스에 적합.
- 인제스천은 GPU 배치 임베딩, 질의 단건은 CPU/GPU 선택(§2 전략).

### 하이브리드 검색 (dense + sparse)
ChromaDB는 BM25를 내장하지 않으므로 **별도 sparse 인덱스**를 둔다.
- **Sparse(BM25)**: `kiwipiepy`로 한국어 형태소 토큰화 → `bm25s`(빠름, 순수 파이썬) 또는
  `rank_bm25`로 인덱스. 영어는 공백/소문자 정규화 병행.
- **Dense**: ChromaDB 벡터 검색.
- **융합**: **RRF(Reciprocal Rank Fusion)** — `score = Σ 1/(k + rank)` (k≈60). 두 랭킹을
  점수 스케일 차이 없이 안정적으로 결합. 가중치 튜닝 파라미터로 노출.
- 근거: 사내 문서는 고유명사·장비명·코드·약어가 많아 정확 매칭(BM25)과 의미 매칭(dense)의
  결합이 단일 방식보다 견고하다.

### 리랭커 (선택, Phase 3)
- `bge-reranker-v2-m3`. top-k 후보를 재정렬해 품질↑.
- 트레이드오프: 품질 이득 vs VRAM(~1.5GB)/지연. §2에 따라 **MVP 미포함**, 필요 시 CPU 실행
  또는 모델 스와핑으로 도입.

## 6. 답변 생성

### 시스템 프롬프트 템플릿(요지)
- **한국어로 답변**한다.
- 제공된 컨텍스트에 **근거가 있을 때만** 답하고, 각 주장에 **출처(문서명·시트/슬라이드/페이지)**를
  표기한다.
- 컨텍스트에 근거가 없으면 **"제공된 문서에서 근거를 찾지 못했습니다"**라고 답한다(환각 금지).
- 표/수치는 원문 값을 보존해 인용한다.

### 출처 표기
- 각 청크 메타의 `source_file` + 위치(시트/슬라이드/페이지)를 답변 하단 근거 목록으로 렌더.
- Streamlit UI에서 근거 청크 원문을 펼쳐 볼 수 있게 제공.

### 컨텍스트 예산
- `num_ctx=4096` 기본. top-k와 청크 크기를 곱해 컨텍스트 상한을 넘지 않도록 동적 트림.
- KV 캐시 VRAM(§2)과 연동: 컨텍스트를 키우면 VRAM/지연이 증가하므로 필요한 만큼만.

## 7. HEX 로그 분석 워크플로우 (핵심 기능)

사용자가 HEX 통신 로그를 업로드하고 질문하면:

1. **후보 검색**: 업로드된 HEX 로그 + 질문(장비명 등 단서)을 바탕으로, 인덱스에서
   `doc_type=protocol_spec` 문서 중 **관련 프로토콜 명세/통신 규격 후보**를 하이브리드 검색.
2. **확인 단계 (필수 · 자동 추측 금지)**: 검색된 후보 문서를 UI에 제시하고
   **"이 문서의 프로토콜이 맞습니까?"** 확인을 받는다. 사용자가 선택/확정하기 전에는
   해석을 진행하지 않는다.
3. **해석·분석**: 확정된 명세의 **패킷 구조·필드·명령 코드** 정의를 컨텍스트로 하여 HEX 로그를
   파싱·해석하고 질문에 답변한다.

**설계 고려사항**
- **컨텍스트 초과 처리**: HEX 로그가 LLM 컨텍스트를 초과하면
  (a) 패킷 경계(길이 필드/구분자/고정 헤더)로 분할, (b) 질문 관련 구간만 추출,
  (c) 요약→상세 2단계 질의. 명세의 패킷 정의 표를 정확히 참조하도록 명세 청크를 우선 컨텍스트에 고정.
- **명세 표 참조 정확도**: 프로토콜 명세의 필드/코드 표를 구조화(가능하면 파싱 시 표를 별도 메타로
  보존)하여 필드 오프셋·바이트 폭을 정확히 인용.
- **모드 구분/전환**: UI에서 **HEX 분석 탭**을 일반 문서 QA와 분리. HEX 파일 업로드가 있을 때만
  이 워크플로우가 활성화되며, 확인 단계 UI가 반드시 개입한다.

## 8. OCR (이미지 처리, Phase 3)

오프라인에서 동작하는 한국어+영어 OCR. 후보 비교:

| 방안 | 오프라인 설치 | VRAM/자원 | 한/영 정확도 | 비고 |
|---|---|---|---|---|
| **PaddleOCR (kor+eng)** | `paddlepaddle` Windows wheel 존재(대용량) + 모델 파일 반입 | GPU ~1–2GB 또는 CPU | 표/문서 OCR 강함 | 모델 가중치 별도 반입 필요 |
| **Tesseract (kor+eng)** | 엔진이 wheel 아님 → **설치 실행파일 + 언어팩 번들** 필요, `pytesseract` 래퍼 | CPU 중심 | 인쇄체 무난, 레이아웃 약함 | 순수 pip 아님(엔진 별도) |
| 경량 비전 LLM | GGUF 반입 | VRAM 경합 | 가변 | 질의 VRAM과 충돌 위험, 후순위 |

- 결론(잠정): **인제스천 시점 실행이라 질의 VRAM과 무경합**이므로 정확도 우선.
  PaddleOCR을 1순위 후보로 하되, 오프라인 반입 난이도(모델·wheel 크기)와 정확도를 실측 후 확정.
  사용자 선호/이미지 비중은 `open_questions.md` Q4로 확인.

## 10. 오프라인 패키징 전략 (가장 중요)

### wheelhouse 구성
개발 PC에서:
```
pip download -r requirements.txt \
  --platform win_amd64 --python-version 3.11 --only-binary=:all: \
  -d wheelhouse/
```
- `--only-binary=:all:` 로 **순수 wheel만** 수집. 소스 배포(sdist)만 있는(=컴파일 필요) 패키지는
  다운로드 단계에서 걸러지므로 **후보에서 배제하거나 대안 제시**.
- 여러 파이썬 마이너 버전이 섞일 수 있으면 3.10/3.11/3.12 각각 받아 둔다.

### 순수 wheel 검증표 (후보 패키지)

| 패키지 | 용도 | Windows 순수 wheel | 비고 |
|---|---|---|---|
| streamlit | UI | ✓ | 의존성 다수, 함께 수집 |
| chromadb | 벡터 DB | ✓(파이썬) | onnxruntime 등 동반 의존성 수집 필요 |
| openpyxl | xlsx | ✓ | |
| python-docx | docx | ✓ | |
| python-pptx | pptx | ✓ | Pillow 동반 |
| charset-normalizer | 인코딩 판별 | ✓ | |
| kiwipiepy | 한국어 형태소 | ✓ | Windows wheel 제공 |
| bm25s / rank_bm25 | BM25 | ✓ | 순수 파이썬 |
| ollama (python client) | LLM/임베딩 호출 | ✓ | 엔진은 별도 설치(기설치) |
| paddleocr / paddlepaddle | OCR(Phase 3) | ✓(대용량) | 모델 가중치 별도 반입 |

> 위 표는 설계 기준 후보이며, **실제 다운로드로 순수 wheel 여부를 확정**하는 것이 §12 구현 단계의
> 첫 검증 항목이다. onnxruntime 등 네이티브 확장은 플랫폼 태그 일치가 관건.

### 설치·진단 스크립트
- `install.bat` / `install.ps1`: 가상환경 생성 → `pip install --no-index --find-links wheelhouse -r requirements.txt`.
- `smoke_test.py`: import 점검 + Ollama 연결/모델 존재 확인 + 임베딩 1건 + 소형 인덱싱→검색 왕복.

### Ollama 모델 이전 절차 (문서화)
- 개발 PC에서 필요한 모델을 받아 `~/.ollama/models` (blobs + manifests) 를 USB로 이전, 또는
  GGUF + `Modelfile`로 `ollama create`. bge-m3-FP16.gguf는 기설치 확인됨 → LLM 태그 확정 후 절차 확정.

### 최종 배포 폴더
```
crypto-rag-dist/
  src/                 소스코드
  wheelhouse/          오프라인 wheel 전체
  models/              (필요 시) GGUF/모델 이전물
  install.bat / .ps1   설치 스크립트
  smoke_test.py        설치 후 자가진단
  docs/                모델 이전 가이드 + 사용자 매뉴얼
```

## 11. 단계별 로드맵

### MVP — 텍스트+표 검색 QA
- 범위: xlsx/docx/pptx/txt 파싱 → 청킹 → ChromaDB(bge-m3) + BM25 → RRF 하이브리드 검색 →
  LLM 출처 표기 답변 → Streamlit UI(문서 QA 탭 + 인덱싱 탭).
- **완료 기준**: 승인된 더미 샘플에 대해 파싱→인덱싱→질의 E2E 동작, 답변에 정확한 출처 표기,
  근거 없을 때 "모른다" 응답.
- **테스트**: 샘플 문서 기반 질문 세트로 검색 재현율/출처 정확도 수동 평가.

### Phase 2 — HEX 로그 분석 워크플로우
- 범위: HEX 업로드 → 프로토콜 명세 후보 검색 → **UI 확인 단계** → 확정 명세 기반 HEX 해석.
- **완료 기준**: 가상 장비 명세 + 그에 맞는 HEX 샘플로, 확인 단계를 거쳐 필드/명령 해석 답변 성공.
  컨텍스트 초과 로그의 분할 처리 동작.
- **테스트**: 명세와 로그가 일치/불일치하는 케이스 각각에서 올바른 후보 제시·확인 흐름 검증.

### Phase 3 — 고도화
- 이미지 OCR(§8), 리랭커(§5), 하이브리드 파라미터 튜닝.
- **완료 기준**: 이미지 포함 문서의 텍스트가 검색에 반영, 리랭커 on/off 품질 비교.

## 12. 개발 진행 절차 (샘플 검토 게이트)

1. **샘플 세트 생성**: 한/영 혼용 xlsx·docx·pptx·txt(표·이미지 포함, 양식 제각각) +
   가상 장비 프로토콜 명세 문서 + 그 명세를 따르는 HEX 통신 로그 샘플.
2. **검토 게이트 (필수)**: 생성한 샘플 목록과 각 파일의 구조·내용 요약을 사용자에게 제시한다.
   사용자가 업무용 PC의 실제 자료와 대조해 "실제는 이런 점이 다르다"고 피드백하면 샘플을 수정한다.
3. **승인 후에만** 해당 샘플 기준으로 파싱→인덱싱→질의 E2E 테스트를 진행한다.
   **승인 전에는 파이프라인 세부 구현을 확정하지 않는다.**
